# Calendar Guard v1

Инструмент для Meta-ассистента: фиксирует структуру календарного блока, сохраняет заметки и дополнительные поля, готовит минимальное обновление Google Calendar. Пользователю не нужно заполнять JSON.

Python 3.11+, без сторонних библиотек. Запуск тестов: `python3 -m unittest -v`.

## Рабочий маршрут

1. Прочитать актуальные Meta/Planner и Calendar. Для каждого изменяемого события вызвать read_event, не использовать сокращённый поиск вместо полного чтения.
2. Подготовить JSON как в `example.json`: полный объект события из коннектора, block и context. В context включить все страницы событий затронутого интервала и защищённые интервалы дорог, сборов, отдыха и резерва из актуальных правил. `complete: true` — утверждение вызывающей стороны о полноте чтения, а не автоматическое доказательство.
3. `python3 guard.py prepare request.json > plan.json`. Код выхода 2 означает запрет записи. Просмотреть diff. Сохранить plan.json в постоянный источник перед записью: он содержит исходное событие для отката. Не складывать туда токены.
4. Снова прочитать событие, передать `{plan, current}` в `check-current`. При изменении остановиться и пересобрать план.
5. Если diff непустой, передать только connector_payload инструменту google_calendar_update_event. Программа выдаёт аргументы для существующего коннектора и сама не имеет сетевого доступа. Для новой задачи сначала сформировать событие в отдельном маршруте создания; v1 здесь поддерживает только обновление существующих событий.
6. Снова read_event, вызвать `verify` с `{plan, current}`; перечитать весь затронутый период и проверить ограничения/резерв. Только после этого отметить операцию успешной и обновить Planner. Не повторять запись вслепую при сетевом сбое.
7. Для отката передать `{plan, current}` в `rollback`. Изменения пользователя после операции блокируют откат. Перед откатом времени повторно проверить полный календарь и подготовить допустимый интервал; сам rollback выдаёт только предложение, не выполняет запись.

## Схема

schema_version=1; kind: work/class/travel/sport/meeting/practice; area; task; task_id (если есть).
Рабочий блок требует result, непустой список actions и fallback. Для остальных типов они необязательны.
materials, conditions, deadline, notes, provenance присутствуют всегда; null явно означает неизвестное. Пустой список означает «не требуется». deadline.kind: confirmed/internal/unknown; подтверждённому сроку нужен source; точный срок передаётся в at с часовым поясом, а неточная дата остаётся value и требует смысловой проверки ассистентом.
flexibility.movable обязателен. Дополнительно min_minutes/max_minutes, not_before/not_after (ISO-8601). splittable хранит разрешение, v1 не выполняет разделение автоматически.
Любые дополнительные ключи сохраняются глубоким слиянием и отображаются отдельным разделом. Старый текст описания остаётся дословно за пределами управляемого раздела. Новые заметки можно добавлять до/после маркеров. Правки внутри раздела требуют согласования перед обновлением — программа не затирает их.

Структурированные данные хранятся в сохранённом plan.json (поле block). Для следующего обновления передать их как previous_block. Если предыдущая структура потеряна, программа блокирует обновление управляемого блока, а не угадывает поля. В описании календаря остаётся только читаемый текст. HTML-обёртки коннектора учитываются при проверке; заметки сохраняются.

## Границы гарантии

Код обеспечивает проверки только при прохождении этого маршрута. Прямые изменения через Calendar или другой инструмент он физически не блокирует. Подключение к утреннему пилоту — инструкция ассистенту запускать проверку, не постоянно работающий сервер и не замена Google Calendar.
Коннектор не предоставляет условную запись If-Match: между последним чтением и записью остаётся окно гонки. v1 обнаруживает изменения при чтении и проверяет результат, но не обещает атомарность на сервере. События с участниками и all-day блоки исключены из автоматической записи. Повторяющееся событие меняется только в одном экземпляре.
Ночное окно работы 23–08 защищено кодом. Фактические восемь часов сна, нагрузку, необходимость задачи и достаточность резервов оценивает Meta по актуальным источникам; программа не может узнать их из одного события. Все внешние ограничения передавать в protected. Факт выполнения из времени не выводится.
Никакие учётные данные не нужны и не поставляются. Новые версии схемы требуют явной миграции. История исходников поставляется вместе с тестами; v1 не устанавливает Git-сервер или хостинг.

Основа семантики частичного обновления: https://developers.google.com/workspace/calendar/api/v3/reference/events/patch

## Статус выполнения — отдельно от плана

Машиночитаемая запись в описании: [AMIR-EXECUTION-STATUS:v1] затем JSON-объект и [/AMIR-EXECUTION-STATUS].
Для создания или обновления вызывайте Calendar_Guard.prepare_block с ключами operation=execution_status, event, execution, context.
Execution: schema_version=1; status=PLANNED|DONE|PARTIAL|CANCELLED_PLAN|UNKNOWN; planned_start/end (исходный план, неизменный после первого сохранения); actual_start/end (подтверждённые фактические границы либо null); evidence (источник факта либо null).
Контекст требует полного чтения затронутого периода. Маршрут: prepare, сохранить план в существующем operation journal, новое read_event + check_current, применить ТОЛЬКО connector_payload через Google Calendar, новое read_event + verify_update, перепроверить период.
Изменение execution_status трогает лишь description выбранного экземпляра; все существующие заметки и Guard-managed раздел остаются неизменными. Результат подготовительного вызова не подтверждает запись в Google Calendar.
PLANNED означает только намерение; DONE и PARTIAL требуют доказуемого источника. Истечение события не означает DONE, отмена события не доказывает пропуск, UNKNOWN не означает провал. Не подставлять запланированное время вместо фактического.
Для отменённых событий Google Calendar status=cancelled: не восстанавливайте экземпляры; запишите соответствующее решение в уже существующий Changes. Исторические события без метки — неизвестны до проверки, не проводите автоматический массовый backfill без фактов.
Текущее event.start/end может отличаться от неизменного planned_start/end: так сравнивается исходный план и подтверждённый факт.
